# Step-by-Step SOC & SOAR Lab Setup Guide

Setup notes for a distributed Wazuh SIEM + Shuffle SOAR + Tailscale Mesh environment. Workflows and response behavior still require validation against the exact installed versions in an isolated lab.

---

## 1. Prerequisites

- **Host Virtualization**: VirtualBox 7.0+ or VMware Workstation 17+
- **Wazuh Manager**: Official all-in-one Wazuh OVA (v4.14+)
- **Operating Systems**:
  - Ubuntu Server 24.04 LTS (2 vCPU, 4 GB RAM)
  - Windows 11 Enterprise (2 vCPU, 4 GB RAM)
  - Windows Server 2022 Standard (2 vCPU, 4 GB RAM)
- **Networking & VPN**: Tailscale Free Plan (Owner-approved mesh tailnet)
- **Automation**: Docker & Docker Compose (for Shuffle SOAR)

---

## 2. Wazuh SIEM Manager Deployment

1. **Import the Official OVA**:
   - Download the Wazuh all-in-one virtual appliance.
   - Import into VirtualBox with **Bridged Adapter** or **NAT Network** with Tailscale enabled.
2. **Rotate the generated credentials before connecting the lab**. Use the [Wazuh password-management guide](https://documentation.wazuh.com/4.14/user-manual/user-administration/password-management.html) and store the resulting secrets in a local password manager. Extracting `wazuh-passwords.txt` only reveals generated credentials; it does not rotate them. Do not print the archive contents into shared logs or terminal recordings.
3. **Join Tailscale Mesh**:
   ```bash
   curl -fsSL https://tailscale.com/install.sh | sh
   sudo tailscale up --accept-routes
   ```
   Note the assigned `100.x.x.10` address.

---

## 3. Tailscale Mesh Network Configuration

1. Log in to the [Tailscale Admin Console](https://login.tailscale.com/admin).
2. Generate an **Invite Link** or Auth Key for team members.
3. Verify all 5 node endpoints appear in the tailnet:
   - `wazuh-manager` (`100.64.0.10`)
   - `ubuntu-victim` (`100.64.0.11`)
   - `win11-victim` (`100.64.0.12`)
   - `win2022-srv` (`100.64.0.13`)
   - `shuffle-soar` (`100.64.0.14`)
4. Keep key-expiry policy appropriate to each device. Disabling expiry can reduce security; only consider it for a trusted, unattended lab server when uptime requires it, and document the trade-off. Leave expiry enabled for human-operated devices. See [Tailscale key expiry](https://tailscale.com/docs/features/access-control/key-expiry).

## 4. Wazuh Agent Enrollment

### Linux (Ubuntu Server)
```bash
: "${WAZUH_REGISTRATION_PASSWORD:?set the enrollment password securely}"
wget https://packages.wazuh.com/4.x/apt/pool/main/w/wazuh-agent/wazuh-agent_4.14.4-1_amd64.deb
sudo env WAZUH_MANAGER='100.64.0.10' WAZUH_AGENT_NAME='agent-demo' WAZUH_REGISTRATION_PASSWORD="$WAZUH_REGISTRATION_PASSWORD" dpkg -i wazuh-agent_4.14.4-1_amd64.deb
sudo systemctl daemon-reload
sudo systemctl enable wazuh-agent
sudo systemctl start wazuh-agent
```

### Windows (11 & Server 2022)
Open an elevated PowerShell prompt:
```powershell
Invoke-WebRequest -Uri https://packages.wazuh.com/4.x/windows/wazuh-agent-4.14.4-1.msi -OutFile wazuh-agent.msi
msiexec.exe /i wazuh-agent.msi /q WAZUH_MANAGER='100.64.0.10' WAZUH_AGENT_NAME='agent-demo' WAZUH_REGISTRATION_SERVER='100.64.0.10' WAZUH_REGISTRATION_PASSWORD="$env:WAZUH_REGISTRATION_PASSWORD"
NET START Wazuh
```

## 5. Shuffle SOAR Deployment (Docker)

1. Clone the Shuffle repository and launch with Docker Compose:
   ```bash
   git clone https://github.com/Shuffle/Shuffle.git
   cd Shuffle
   docker compose up -d
   ```
2. Access Shuffle at `http://100.64.0.14:3001`.
3. Create a Shuffle workflow in the UI. The committed JSON is a design reference, not a native Shuffle export that can be imported directly; validate each app and branch in the installed Shuffle version.
4. Configure environment variables in Shuffle:
   - `VIRUSTOTAL_API_KEY`: Your VirusTotal API Key.
   - Configure a dedicated, least-privilege Wazuh API user for the required action. Store its credentials in Shuffle's secret mechanism; do not use built-in dashboard credentials.

Store real values only in Shuffle's local secret/configuration mechanism. The example above is a placeholder; never commit credentials, tokens, generated webhook URLs, or screenshots containing them.

## 6. Configuring the Wazuh-to-Shuffle Webhook

Edit `/var/ossec/etc/ossec.conf` on the Wazuh Manager:

```xml
<integration>
  <name>custom-shuffle</name>
  <hook_url>http://shuffle.example.invalid/api/v1/hooks/REPLACE_WITH_WEBHOOK_ID</hook_url>
  <level>6</level>
  <rule_id>100003,100004,100006,100005</rule_id>
  <alert_format>json</alert_format>
</integration>
```

Install the executable whose name matches the integration. Replace the example URL with the private URL generated by your Shuffle instance:

```bash
sudo install -o root -g wazuh -m 750 configs/integrations/custom-shuffle /var/ossec/integrations/custom-shuffle
```

Restart the Wazuh Manager daemon:
```bash
sudo systemctl restart wazuh-manager
```

Verify webhook transmission by monitoring `/var/ossec/logs/ossec.log`:
```bash
tail -f /var/ossec/logs/ossec.log | grep -i custom-shuffle
```

## 7. Active-Response Scripts: Deployment Gap (Read Before Testing Containment)

The committed scripts in `configs/scripts/` are reference copies. Nothing in this repository shows them deployed to an agent or executed on one, and the offline checks do not validate that step.

- **Linux (`firewall-drop.sh`)**: copy the script to the Linux agent's active-response directory (for example `/var/ossec/active-response/bin/firewall-drop.sh`), set ownership/permissions for the agent user, and restart the agent. The stock Wazuh agent already ships a `firewall-drop` script; decide explicitly whether you are replacing it with this copy or using the stock one.
- **Windows (`netsh-isolate.cmd`)**: the manager config (`configs/ossec.conf`) registers a command named `netsh-isolate` with executable `netsh.cmd`, but the committed file is named `netsh-isolate.cmd`. Resolve this mismatch before testing — either rename/copy the file to the configured executable name on the agent's `active-response\bin` directory, or change the command definition to match the file. Do not assume the committed file is what would run.
- **Rule `100006` has no direct active-response binding** in `configs/ossec.conf`. Containment for the C2 scenario depends entirely on the Shuffle REST API callback path, which is not runtime-validated.
- Test containment only on an isolated, disposable endpoint with a recovery path. Confirm the block in `active-responses.log` on the agent and the corresponding alert on the manager; a configured binding alone is not proof it ran.
